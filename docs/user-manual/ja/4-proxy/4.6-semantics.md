# 4.6 プロキシの動作仕様: 何が失敗として扱われるか

前のページでは画面の操作を説明しました。このページでは、プロキシがいつフェイルオーバーし、いつ諦め、ディスク上の何を変更するかを予測できるよう、プロキシが従うルールを説明します。内容は `src-tauri/src/proxy/`（v3.17.0 以降）に基づいています。

## どのプロバイダをどの順で試すか

| アプリの自動フェイルオーバー | 試すプロバイダ |
| --- | --- |
| **オフ** | 現在のプロバイダのみ。サーキットブレーカーは参照せず、下記の段階別タイムアウトも適用されません（レスポンスヘッダー待ちの上限 600 秒のみ）。エラーはそのままツールに返ります |
| **オン** | **フェイルオーバーキューの順**（P1 → P2 → …）に試し、ブレーカーが開いているプロバイダはスキップします。現在のプロバイダが P1 でない限り、それが最初に試されることはありません |

1 リクエストで試すプロバイダは最大 `リトライ回数 + 1` 個です（既定のリトライは 3 回なので最大 4 個）。キュー内のすべてのブレーカーが開いている場合は「全プロバイダがサーキットブレーク中」（`FO-004`）、キューが空の場合は「プロバイダ未設定」（`FO-005`）で失敗します。

## どのエラーでフェイルオーバーするか

| 試行の結果 | 次のプロバイダへ？ | ブレーカーに計上？ |
| --- | --- | --- |
| 接続拒否 / DNS / TLS エラー | はい | はい |
| 接続タイムアウト（10 秒） | はい | はい |
| ストリーミング: **初回バイトタイムアウト** 内にヘッダーと最初のチャンクが届かない | はい | はい |
| ストリーミング: 最初のチャンクの後、**アイドルタイムアウト** の間データがない（まだツールに何も送っていない場合） | はい | はい |
| 非ストリーミング: **非ストリーミングタイムアウト** 内に完全なレスポンスが届かない | はい | はい |
| HTTP **401、403、404、408、409、429、451** と、下に挙げていないその他の 4xx | はい | はい |
| HTTP **5xx**（501 を除く） | はい | はい |
| HTTP 2xx だが本文がエラーエンベロープ、またはストリームがエラーイベントで始まる | はい（空の応答を返さずに失敗として扱う） | はい |
| HTTP **400、405、406、413、414、415、422**（リクエスト自体が不正） | **いいえ**、ツールに返す | いいえ |
| HTTP **501**（上流がこの API を実装していない） | **いいえ** | いいえ |
| ツールがリクエストをキャンセルした | いいえ | いいえ |
| Codex 公式（ChatGPT）アカウントの 401 / 403 | **いいえ**: ログインは Codex のものであり、プロバイダを切り替えると会話が気付かないうちに別の場所へ移ってしまうため | いいえ |

ストリーミングレスポンスの最初のデータをツールに送った後は、プロバイダを切り替えられません。その後の失敗はエラーとしてそのレスポンスを終了させます。

一部の組み込み修正（thinking 署名レクティファイア、thinking 予算レクティファイア）は、上表で分類する前に、修正したリクエストで **同じ** プロバイダに一度だけ再試行します。

## タイムアウト

プロキシパネルでアプリごとに設定し、`0` でその段階を無効にします。既定値:

| タイムアウト | 既定値 | 計測の起点 |
| --- | --- | --- |
| 接続 | 10 秒（固定） | TCP/TLS 接続の確立 |
| ストリーミング初回バイト | 60 秒 | リクエスト送信から最初のチャンク（ヘッダーを含む）まで |
| ストリーミングアイドル | 120 秒 | チャンクとチャンクの間 |
| 非ストリーミング | 600 秒 | リクエスト送信からレスポンス本文の受信完了まで |

フェイルオーバーがオフの場合は、接続タイムアウトとレスポンスヘッダーの上限 600 秒だけが適用されます。

## サーキットブレーカー

ブレーカーはアプリごと・プロバイダごとに独立しています（`app:provider`）。既定値（プロキシ設定で変更可能）:

| 状態 | 意味 | 状態が変わる条件 |
| --- | --- | --- |
| **クローズ** | 通常どおり通す | **4 回連続の失敗**、または 60 秒以内の直近 **10** 件のエラー率が **60%** 以上 → オープン |
| **オープン** | そのプロバイダをスキップ | **60 秒** 後 → ハーフオープン |
| **ハーフオープン** | 一度に 1 件だけ試行リクエストを通す | **2 回成功** → クローズ、失敗 → 再びオープン |

ブレーカーの状態を変えるのは上表の「ブレーカーに計上」の結果だけです。不正なリクエスト（400、422 など）やキャンセルは計上されないため、問題のあるクライアントがすべてのブレーカーを開いてしまうことはありません。

## テイクオーバーがディスク上で変更するもの

アプリのテイクオーバーをオンにすると（4.2）:

1. そのアプリの現在のライブ設定がデータベース（`proxy_live_backup`）に保存されます。
2. ライブ設定がプロキシを指すように書き換えられ（例: Claude の `settings.json` の `ANTHROPIC_BASE_URL` = `http://127.0.0.1:15721`）、本物の API キーはプレースホルダー `PROXY_MANAGED` に置き換えられます。転送時にプロキシが本物のキーを付けます。
3. テイクオーバーをオフにする（またはプロキシを停止する）と、保存したコピーが書き戻されます。
4. テイクオーバー中に CC Switch がクラッシュ・強制終了した場合、次回起動時に残ったプレースホルダーやバックアップを検出し、元の設定を自動的に復元します。

テイクオーバー中にプロバイダを切り替えると、変わるのはプロキシの転送先です。ツール自身の設定ファイルはプロキシを指したままです。

## ログの見方

上記の判断はすべてコード付きで `~/.cc-switch/logs/cc-switch.log` に記録されます（例: `FO-004` は全プロバイダがサーキットブレーク中）。ログの場所は [5.6 トラブルシューティング](../5-faq/5.6-troubleshooting.md)、キューとヘルス表示は [4.3 フェイルオーバー](./4.3-failover.md) を参照してください。
