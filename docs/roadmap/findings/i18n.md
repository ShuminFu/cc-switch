# Internationalization — findings (I18N-xx)

Part of the [next-phase proposals](../README.md). 20 findings. Priorities: P1 = 6, P2 = 9, P3 = 5.

## Area summary

The four UI locales (`src/i18n/locales/{en,zh,zh-TW,ja}.json`) are structurally healthy: 2,583 flattened keys in en/zh/ja, identical key order, 0 placeholder mismatches, 0 whitespace defects, 0 duplicate keys inside a file; the only parity gap is zh-TW with 30 missing keys (all `settings.tool*` tool-lifecycle strings, now rendered in English via `fallbackLng: "en"`) plus 2 orphan keys. Cross-referencing 2,394 literal `t()` calls (1,838 distinct keys, 14 template-literal and 39 dynamic-expression calls marked unverifiable) found 10 keys used in code but absent from every locale — each falls back to a hard-coded Chinese `defaultValue`, so English/Japanese/Traditional-Chinese users see Simplified Chinese toasts (e.g. `usage.unpriced` → "未定价") — and ~444 en keys (17%) that no code path references (the whole `console.*` namespace, 53 `omo.*`, 45 `proxy.*`, 44 `mcp.*`). Beyond JSON, the i18n boundary is porous: 802 `defaultValue:` fallbacks of which 459 are Chinese plus 195 positional `t("key", "中文")` defaults, ~247 CJK string literals outside `t()` (zod/JSON validation messages), and a Rust backend whose user-facing errors are Chinese-only (525 `Err/format!` lines, 53 `#[error("…")]` attributes, 228 commands returning `Result<_, String>`), which the frontend then matches by Chinese substring (`src/utils/errorUtils.ts:45-110`); proxy HTTP error bodies sent to Claude Code/Codex are Chinese too. First-run language detection falls back to `zh` for any non-CJK/non-English OS locale on both the frontend (`src/i18n/index.ts:11,57`) and the tray (`src-tauri/src/tray.rs:80-83,90-94`), so a German or Korean user gets a Chinese UI even though a German README exists. Process-wise, CONTRIBUTING.md still names three languages and the wrong paths, `.github/labeler.yml` watches a non-existent `src/locales/**`, `pnpm lint` is referenced but not defined, and CI (`.github/workflows/ci.yml`) has no locale-parity, dead-key or hard-coded-string check. On documentation: all four READMEs share an identical 589-line skeleton (11 FAQ items, 14 feature bullets each) but link release notes for v3.16.1 while the app is 3.17.0, the trilingual user manual (3×26 files) is stamped v3.16.0/2026-05-29 and has zero mentions of Grok Build, project profiles or S3 sync, the deep-link manual/generator cover 5/3 apps while the parser accepts 7, the README screenshots show a 3-app UI, 4 old versions lack Japanese release notes, 14 relative links in v3.7–3.8 release notes are broken, the CHANGELOG lacks a 3.6.1 entry and has a 3.5.0 date out of sequence. Onboarding is a single first-run modal whose text names only three tools, with no setup wizard, no in-app link to the manual, no in-app "what's new", and undocumented keyboard shortcuts.

## Findings

### I18N-01: Ten keys used in code are missing from every locale and leak Chinese fallbacks into non-Chinese UIs

**Type:** bug · **Priority:** P1 · **Effort:** S · **Confidence:** high

- **Evidence:** `key_usage.py` output "Keys used in code (literal) but missing in en.json: count: 10": `claudeDesktop.route.stopBlockedByTakeover` (`src/components/proxy/ClaudeDesktopRouteToggle.tsx:44-47`), `codexConfig.noCommonConfigToApply` (`src/components/providers/forms/hooks/useCodexCommonConfig.ts:324-326`), `failover.tooltip.takeoverRequired` (`src/components/proxy/FailoverToggle.tsx:45-48`), `notifications.proxyReasonClaudeDesktop` (`src/hooks/useProviderActions.ts:218-220`), `provider.duplicateLiveIdsLoadFailed` (`src/App.tsx:757-759`), `providerForm.providerKeyStatusLoading` (`src/components/providers/forms/ProviderForm.tsx:1071-1073`), `providerForm.requiredFields` (`src/components/providers/forms/GrokBuildProviderForm.tsx:303-306`), `proxy.server.stopped` / `proxy.server.stopFailed` (`src/hooks/useProxyStatus.ts:71-85`), `usage.unpriced` (`src/components/usage/RequestDetailPanel.tsx:289`, `RequestLogTable.tsx:280`: `t("usage.unpriced", "未定价")`). `rg unpriced src/i18n/locales/` returns nothing.
- **Problem:** Every one of these calls carries a Simplified-Chinese `defaultValue`, so in the en/ja/zh-TW UI the toast/tooltip/label is rendered in Chinese (e.g. "代理服务已停止" when stopping the proxy, "未定价" in the usage log). `src/i18n/index.ts:76-91` sets no `missingKeyHandler`/`saveMissing`, so nothing flags this at runtime.
- **Proposal:** Add the 10 keys to all four locale files (English source text first), then make missing keys impossible to ship via the lint in I18N-05 and typed keys in I18N-11. As a stop-gap policy, forbid non-English `defaultValue` (see I18N-08).
- **Acceptance:** `python3 -I key_usage.py` reports `count: 0` for missing-in-en; switching the UI to English and stopping the proxy shows an English toast; the usage request log shows "Unpriced" not "未定价".

### I18N-02: First-run language falls back to Simplified Chinese for every non-CJK, non-English OS locale (frontend, tray and backend)

**Type:** bug · **Priority:** P1 · **Effort:** S · **Confidence:** high

- **Evidence:** `src/i18n/index.ts:11` `const DEFAULT_LANGUAGE: Language = "zh"` and `:57` `return DEFAULT_LANGUAGE` after only zh/ja/en prefixes are matched; `src-tauri/src/tray.rs:66-83` `map_locale_to_tray_language` ends with `else { "zh" }` and `:89-94` `detect_system_tray_language()` `.unwrap_or("zh")` (introduced by commit 997be22 "detect system locale for first-run language instead of hardcoding zh", whose message itself says "otherwise zh"); `src-tauri/src/commands/config.rs:21-23` `.unwrap_or_else(|| "zh".to_string())`; `src/hooks/useSettingsForm.ts:80` `useRef<Language>("zh")`; `src/index.html:2` `<html lang="zh-CN">` and `:6` `<title>Claude Code 供应商切换器</title>`; `tests/setupTests.ts:13-14` `lng: "zh", fallbackLng: "zh"`.
- **Problem:** A user with a de-DE, fr-FR, ko-KR, es-ES, pt-BR or ru-RU system gets a Chinese UI and Chinese tray on first launch and must find the language switcher in Chinese; this contradicts the shipped `README_DE.md`. The `<html lang>` is also wrong for screen readers and font selection in every non-zh language.
- **Proposal:** Change the unknown-locale fallback to `en` on all three sides (`index.ts`, `tray.rs`, `commands/config.rs`), keep `zh` only for `zh*` locales, set `document.documentElement.lang` on `languageChanged`, give `src/index.html` a neutral `lang="en"` and the product name as title, and export `getInitialLanguage` so it can be unit-tested (currently unexported, `src/i18n/index.ts:13`).
- **Acceptance:** Unit tests for `getInitialLanguage("de-DE") === "en"`, `("zh-HK") === "zh-TW"`, `("ja-JP") === "ja"`; Rust test `map_locale_to_tray_language("de-DE") == "en"`; `document.documentElement.lang` equals the active i18n language in a component test.

### I18N-03: Backend user-facing errors are Chinese-only strings matched by substring on the frontend

**Type:** tech-debt · **Priority:** P1 · **Effort:** XL · **Confidence:** high

- **Evidence:** `rg -n "(Err\(|format!\(|anyhow!\(|bail!\().*[\p{Han}]" src-tauri/src` = 525 lines; `#[error("…Han…")]` attributes = 53 (`src-tauri/src/error.rs:8-62`, e.g. `#[error("配置错误: {0}")]`, `#[error("所有供应商已熔断，无可用渠道")]`); 228 `Result<_, String>` command signatures under `src-tauri/src/commands/`; the only localized path is `src-tauri/src/commands/config.rs:20-42` (en/ja/zh — no zh-TW branch, default zh); `AppError::Localized {key, zh, en}` (`error.rs:50-55`) renders as `"{zh} ({en})"` and is used in 10 places; frontend `src/utils/errorUtils.ts:45-110` `translateMcpBackendError` matches 20+ Chinese substrings such as `"MCP 服务器 ID 不能为空"`; 8 toasts surface the raw string (`src/hooks/useGlobalProxy.ts:78`, `src/components/settings/LogConfigPanel.tsx:40`, `RectifierConfigPanel.tsx:47,59`, `SkillStorageLocationSettings.tsx:64`, `src/components/usage/ModelsDevPickerDialog.tsx:239`, `PricingEditModal.tsx:84`, `src/components/providers/ProviderList.tsx:243`) and 36 more interpolate it as `{{error}}`.
- **Problem:** Non-Chinese users get mixed-language error toasts; translations are impossible without touching Rust; the substring mapping silently breaks whenever a Rust message is reworded; adding a locale requires a fourth language branch in Rust.
- **Proposal:** Adopt the pattern already used for skills (`src-tauri/src/commands/skill.rs:249` emits `{code, context, suggestion}` JSON parsed by `src/lib/errors/skillErrorParser.ts:15-60`): make `AppError` serialize to `{code, params, debug}` for all Tauri commands (a `#[serde(tag)]` enum or a `code()` method), keep the Chinese/English `Display` for logs only, and translate on the frontend under an `errors.<code>` namespace with a generic "Unknown error (copy details)" presenter. Migrate namespace by namespace (proxy, provider, mcp first), delete `translateMcpBackendError` when done.
- **Acceptance:** `rg "Result<[^>]*, String>" src-tauri/src/commands | wc -l` trends to 0; `errorUtils.ts` contains no CJK; a test switches locale to en and asserts an MCP validation failure toast contains no CJK characters.

### I18N-05: No automated i18n integrity check in CI; the i18n PR label can never fire

**Type:** ci · **Priority:** P1 · **Effort:** M · **Confidence:** high

- **Evidence:** `.github/workflows/ci.yml:48-56` runs only `pnpm typecheck`, `pnpm format:check`, `pnpm test:unit`; `package.json:5-16` has no i18n or lint script; `tests/` contains no test loading `src/i18n/locales` (`rg -l "i18n/locales" tests` → none; `tests/setupTests.ts:15-18` initialises i18next with empty resources); `.github/labeler.yml:23-26` labels `i18n` on `src/locales/**` which does not exist (real path `src/i18n/locales/*.json`); `.github/pull_request_template.md:25` relies on a manual checkbox; `src/i18n/index.ts:91` `debug: false` and no `missingKeyHandler`.
- **Problem:** The defects in I18N-01/I18N-04 shipped in a release (3.17.0) because nothing validates key parity, placeholder sets, missing keys referenced by code, or dead keys; the i18n label used for triage never applies.
- **Proposal:** Add `scripts/i18n-check.(ts|py)` (port of the two audit scripts: parity, extra keys, `{{var}}` set equality, keys-in-code-missing-in-en with an allowlist for the 14 template prefixes, dead-key report as warning) and wire it as `pnpm i18n:check` into `ci.yml` and the PR checklist; fix `labeler.yml` to `src/i18n/locales/**`; add a vitest that loads real `en.json` into i18next and renders the main views asserting no `t()` returned its own key. Enable `saveMissing`/`missingKeyHandler` → `console.warn` in dev builds.
- **Acceptance:** CI fails on a PR that adds a key to `en.json` only, or references a non-existent key in a literal `t()` call; the `i18n` label is applied to a PR touching `src/i18n/locales/zh.json`.

### I18N-07: ~444 locale keys (17%) are unreachable from code

**Type:** tech-debt · **Priority:** P2 · **Effort:** M · **Confidence:** medium

- **Evidence:** `key_usage.py` + `dead_refine.py`: 755 en keys have no literal `t()` reference; after crediting 236 indirect string-literal references (`labelKey:` tables), 60 template-prefix matches and 14 concatenation-prefix matches, 444 remain with no reference in `src/`, `tests/` or `src-tauri/src`. By namespace: omo 53, proxy 45, mcp 44, providerForm 32, settings 31, skills 27, openclawConfig 23, provider 23, usage 18, console 17 (entire `console.*` namespace unused), header 8 (`header.switchToChinese`, `header.switchToEnglish`, `header.toggleDarkMode` …). Spot checks: `rg "omo.addProfile|proxy.settings.title|header.switchToChinese|console.getVersionFailed|sessionManager.openInTerminal" src` → no hits. Full list in `scratchpad/i18n-tools/dead_refined.json`.
- **Problem:** Translators maintain ~1,800 dead strings across three target locales; dead keys mask real coverage numbers and make reviews noisy. Static analysis cannot see keys assembled at runtime (39 dynamic calls, e.g. `t(preset.nameKey)`, `t(TIER_I18N_KEYS[tier.name])`), so the list needs a human pass.
- **Proposal:** Review the list namespace by namespace; delete keys whose namespace owner confirms removal (start with `console.*`, `header.*`, `proxyConfig.*`, `presetSelector.*`); for keys built dynamically, add a `// i18n-keys: usage.appFilter.*` annotation convention the lint can read; make the dead-key report a CI warning with a baseline file so it cannot grow.
- **Acceptance:** Dead-key count below 100 with a committed allowlist; `pnpm i18n:check` fails when a new unreferenced key is added without an allowlist entry.

### I18N-08: 654 Chinese fallback strings and ~247 hard-coded CJK literals bypass the locale files

**Type:** tech-debt · **Priority:** P2 · **Effort:** L · **Confidence:** high

- **Evidence:** `rg "defaultValue:" src` = 802, of which Chinese = 459 and English = 196; positional `t("key", "中文")` = 195; worst files `src/components/sessions/SessionManagerPage.tsx` (43), `src/components/providers/forms/CodexFormFields.tsx` (37), `src/components/proxy/ProxyPanel.tsx` (31); CJK literals outside `t()`/`defaultValue`/comments ≈ 247 lines, including user-visible validation text: `src/lib/schemas/provider.ts:8,17,25` ("配置 JSON 格式错误"…), `src/utils/providerConfigUtils.ts:75-114` (`fieldName = "配置"`, "JSON格式错误，请检查语法"), `src/utils/tomlUtils.ts:93`, `src/hooks/useStreamCheck.ts:59`, `src/hooks/useImportExport.ts:122`, `src/main.tsx:53`, `src/components/proxy/AutoFailoverConfigPanel.tsx:155`.
- **Problem:** Any missing key degrades to Chinese rather than English (the declared `fallbackLng`), and the zod/JSON validation messages are Chinese in every locale. The English `defaultValue`s are also a second, unreviewed copy of `en.json`.
- **Proposal:** Policy "source strings live in `en.json`; `defaultValue` is forbidden" enforced by an ESLint rule (`eslint-plugin-i18next/no-literal-string` with a CJK-aware regex, plus a custom rule banning `defaultValue`/positional defaults); move the zod and config-validation messages behind `t()` (pass `t` into the schema factory). Do it file by file starting with the three worst files.
- **Acceptance:** `rg "defaultValue:" src | wc -l` = 0; `rg "[\p{Han}]" src --glob '!src/i18n/**' | rg -v '^\S+:\d+:\s*//'` only hits data tables (icon metadata, preset names); lint rule active in CI.

### I18N-09: No plural handling — 42 `{{count}}` strings use "(s)" hacks and inconsistent singular/plural

**Type:** bug · **Priority:** P2 · **Effort:** M · **Confidence:** high

- **Evidence:** `locale_audit.py` "plural-suffixed keys=0; keys with {{count}} placeholder=42", e.g. `settings.skillStorage.confirmMessage` "{{count}} skill(s) will be moved", `copilot.accountCount` "{{count}} account(s)", `mcp.serverCount` "{{count}} MCP server(s) configured", `usage.daysAgo` "{{count}} day ago" vs `sessionManager.daysAgo` "{{count}} days ago", `sessionManager.batchDeleteSuccess` "Deleted {{count}} sessions"; `src/i18n/index.ts:76-91` configures no plural options.
- **Problem:** English shows "1 days ago"/"3 day ago" depending on the namespace; future locales with real plural categories (ru, pl, ar) cannot be expressed; "(s)" reads as unfinished UI.
- **Proposal:** Use i18next JSON-v4 plural suffixes (`_one`/`_other`, i18next ^25 is already a dependency) for the 42 strings; keep CJK locales on `_other` only; add a lint that flags `(s)` in en values and `{{count}}` keys without plural forms.
- **Acceptance:** `rg "\(s\)" src/i18n/locales/en.json` → 0; rendering `usage.daysAgo` with count 1 and 3 yields "1 day ago"/"3 days ago" in a unit test.

### I18N-10: Dates, relative times and collation partly follow the OS locale instead of the app language

**Type:** bug · **Priority:** P2 · **Effort:** M · **Confidence:** high

- **Evidence:** 7 locale-less calls: `src/components/sessions/utils.ts:91,109` (`toLocaleString()`, `toLocaleDateString()`), `src/components/settings/BackupListSection.tsx:44`, `src/components/settings/WebdavSyncSection.tsx:153,939,953`, `src/components/skills/UnifiedSkillsPanel.tsx:64`; hand-rolled relative time in three places (`src/components/sessions/utils.ts:95-110`, `src/components/UsageFooter.tsx:442-448`, `src/components/SubscriptionQuotaFooter.tsx:90-93`) instead of `Intl.RelativeTimeFormat`; `src/hooks/useDragSort.ts:21-26` maps only zh/zh-TW to a collation locale (ja falls to `en-US`); meanwhile `src/components/usage/format.ts:14-22,45-57` already has `fmtInt(locale)` and `getLocaleFromLanguage()` and `UsageDateRangePicker.tsx:174,432` uses `Intl.DateTimeFormat(locale)` correctly. 36 `Intl`/`toLocale*` call sites in total.

### I18N-11: No compile-time key safety (typed i18next resources)

### I18N-12: Proxy HTTP error bodies returned to CLI clients are Chinese

### I18N-20: Component tests run with empty translation resources, so key regressions are invisible

**Type:** ci · **Priority:** P3 · **Effort:** S · **Confidence:** high

- **Evidence:** `tests/setupTests.ts:12-22` initialises i18next with `resources: { zh: { translation: {} }, en: { translation: {} } }` and `fallbackLng: "zh"`; 146 components use `useTranslation`; 10 test files reference i18n (e.g. `tests/components/SettingsDialog.test.tsx`).
