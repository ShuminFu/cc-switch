# Proxy providers & format conversion — findings (PROV-xx)

Part of the [next-phase proposals](../README.md). 33 findings. Priorities: P2 = 23, P3 = 10.

## Area summary

The provider/format layer is large (~36k lines in scope, ~600 unit tests) and handles an impressive matrix of gateway quirks: unmarked-SSE sniffing, EOF-without-blank-line, `[1m]` model markers, DeepSeek/Kimi `reasoning_content` placeholders, Codex OAuth protocol constraints, Gemini missing-id synthesis. Its main structural risk is that four wire protocols (Anthropic Messages, OpenAI Chat, OpenAI Responses, Gemini) are bridged by roughly thirteen hand-written, mutually independent codecs (five request transforms, five streaming converters, three SSE aggregators), so every fix lands in one path and drifts from the others: the three recent commits (#5508 reasoning forward-attach, #5310 streamed tool-call identity, #4706 parameters type normalization) are complete on the Codex↔Chat/Responses paths but are not mirrored in the older Claude↔Chat path (`transform.rs`/`streaming.rs`), which still silently drops upstream error chunks, requires `tool_calls[].index`, ignores provider thinking parameters, and only normalizes schemas when `type` is absent. The Gemini bridge is the weakest leg: thinking is neither requested nor surfaced, streamed text uses an ambiguous prefix heuristic, replay state lives in a volatile in-memory shadow store, and unsupported `format` values can leak into the restricted schema channel. Usage accounting is internally consistent today, but the "does input include cache" rule is encoded as `app_type` string matches in three places plus implicit subtraction inside each transform. Auth managers are reasonable but store secrets in plaintext and have no HTTP-mocked tests for refresh/single-flight behaviour. Suggested direction for the next phase: (1) fix the P1 stream-correctness bugs, (2) introduce a canonical message/stream IR with per-protocol codecs and a bridge registry so each wire-format concern is implemented once, (3) back it with recorded golden fixtures plus round-trip property tests, then (4) close the provider matrix gaps (Gemini thinking, Azure/Bedrock/Vertex, Gemini OAuth refresh).

## Findings

### PROV-01: Claude←OpenAI-Chat stream converter silently swallows upstream error chunks and unparsable payloads

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** `src-tauri/src/proxy/providers/streaming.rs:209-210` — `if let Ok(chunk) = serde_json::from_str::<OpenAIStreamChunk>(data)` with no `else`; a `data: {"error":{...}}` chunk, or any chunk that fails the strict struct (e.g. `choices[].delta` missing, `prompt_tokens: null`), is dropped without logging. `streaming.rs:647-670` only emits terminal events when `pending_message_delta` exists, so a stream consisting of an error chunk + `[DONE]` yields a bare `message_stop` (line 200-205) with no `message_start` and no `error` event. Contrast `streaming_codex_chat.rs:777-782` (detects `event: error` / `chunk.error` and emits `response.failed`) and `streaming_responses.rs:1260-1271` (`response.failed`/`error` → Anthropic `error` SSE), and the non-stream aggregator `handlers.rs:2065-2085` which already handles both error shapes.
- **Problem:** With an `openai_chat` provider (OpenRouter, DeepSeek, Kimi, GitHub Copilot), a mid-stream quota/rate-limit error delivered as a JSON chunk produces an HTTP 200 stream that ends with `message_stop` and no content; Claude Code shows an empty reply or hangs with no diagnostic, and the usage collector records nothing. Parse failures from lenient schemas have the same effect.
- **Proposal:** Parse each `data:` payload as `Value` first; if `event == "error"` or `payload.error` has a reportable message (reuse `error_event_message` from handlers.rs), emit the Anthropic `error` SSE and terminate; otherwise deserialize into `OpenAIStreamChunk` and `log::warn!` on failure. Make `StreamChoice.delta` default and the `Usage` numeric fields `Option`/`deserialize_with` null-tolerant. If the stream ends with no `message_start` sent, emit `error{type:"stream_truncated"}` instead of a bare `message_stop` (mirror `streaming_responses.rs:1526-1533`).
- **Acceptance:** New tests in `streaming.rs`: `{"error":{"message":"quota"}}` chunk → `event: error` and no `message_stop`; chunk without `delta` does not drop the finish_reason; stream with only `[DONE]` emits an error, not `message_stop`.
- **Verification:** **confirmed** — streaming.rs:209 `if let Ok(chunk) = serde_json::from_str::<OpenAIStreamChunk>(data)` has no else arm (the block closes straight into the outer `Err(e)` arm at ~609), `StreamChoice.delta` (line 27) is non-default and `Usage.prompt_tokens: u32` (line 64, serde default does not accept explicit null) confirm the lenient-schema drops; one nuance is that `OpenAIStreamChunk` has no `deny_unknown_fields`, so `data: {"error":{...}}` actually parses successfully as an empty chunk (choices=[]) and is ignored with only a debug log - same effect, different mechanism. The `[DONE]` arm at lines 189-207 emits `message_stop` unconditionally with no `has_sent_message_start` check and the end-of-stream block at 647-670 only emits terminal events when `pending_message_delta` exists, so error+[DONE] yields a bare message_stop and error-without-DONE yields an empty 200 body. No mitigation found: forwarder.rs:2397 `prime_streaming_response` only awaits the first chunk without inspecting it, `validate_responses_stream_start` (forwarder.rs:2202) is gated to openai_responses, and the streaming.rs tests (1118-1248) only cover a transport `Err`, never an in-band error chunk; the contrasts at streaming_codex_chat.rs:777-782 and handlers.rs:2065-2085 (C18/C12) are as described, and handlers.rs:447-480 confirms no usage row is written when no usage events arrive. Downgraded to P2: it is a diagnostics/robustness gap (empty reply, nothing logged above debug) for a desktop proxy rather than exploitable or data-loss; the 'Claude Code hangs' claim is unverifiable by reading. The proposal is sound and not implemented (streaming_codex_chat.rs:806-816 and streaming_responses.rs:1526-1533 already do the stream_truncated form).

### PROV-02: Streamed `tool_calls` without `index` are dropped (streaming.rs) or collapsed (streaming_codex_chat.rs)

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** medium

- **Evidence:** `src-tauri/src/proxy/providers/streaming.rs:44-46` — `struct DeltaToolCall { index: usize, ... }` has no `#[serde(default)]`, so a chunk whose tool call omits `index` fails deserialization and the whole chunk (including any text in the same delta) is discarded via the `if let Ok` at line 209. `streaming_codex_chat.rs:336` — `tool_call.get("index")...unwrap_or(0)`: missing indexes make every parallel call share key 0, so their `id`/`name`/`arguments` overwrite and concatenate into one call (`streaming_codex_chat.rs:357-370`). The team has already met sparse/missing identity upstreams (`handlers.rs` test `chat_sse_to_response_value_backfills_sparse_tool_call_ids`, #5310), yet the three Chat-SSE consumers disagree.
- **Problem:** Providers that omit `index` on streamed tool calls (several OpenAI-compatible gateways and local servers do) lose tool calls entirely on the Claude path or merge parallel calls on the Codex path; neither failure is logged.
- **Proposal:** Share one `ChatToolCallDeltaTracker` between `streaming.rs`, `streaming_codex_chat.rs` and `handlers.rs::chat_sse_to_response_value`: key by `index` when present, else by `id` when present, else open a new slot per chunk that carries a new `id`/`name` and append args to the most recent open slot. Make `index` `Option<usize>` in `DeltaToolCall`.
- **Acceptance:** Tests feeding two parallel tool calls without `index` (distinct ids) through all three consumers produce two distinct `tool_use`/`function_call` items with correct arguments; a text delta in the same chunk is not lost.
- **Verification:** **partially-confirmed** — streaming.rs:44-46 `DeltaToolCall { index: usize, ... }` has no serde default, so a tool call without `index` fails the whole chunk at line 209 and is dropped silently (any text in the same delta included); streaming_codex_chat.rs:336 `unwrap_or(0)` collapses index-less calls into slot 0 where lines 357-370 overwrite id/name and append args, and once the slot is `added` by flush_ready_tool_calls (403-456) later args are emitted to the same item (382-390). handlers.rs:2296-2304 `merge_tool_call_delta` instead falls back to array position, so the three consumers genuinely disagree, and no test in either streaming file feeds an index-less call. Details off: the cited test `chat_sse_to_response_value_backfills_sparse_tool_call_ids` (handlers.rs:2620-2632) covers sparse index holes and missing ids, not missing index, and #5310 (commit 6d316c0) only touched late identity/order in streaming_codex_chat.rs; the likelihood claim ('several gateways and local servers omit index') has no support in the repo - the only index-less shape the team documents is message-shaped fake streams (handlers.rs:2292-2294, test at 2597), which streaming.rs already rejects on the required `delta` field (line 27) before index matters. Kept as a real silent tool-loss bug but downgraded to P2 for a minority of non-compliant upstreams; the shared-tracker proposal is sound but is an M-sized refactor across three consumers, not S.

### PROV-04: Claude→`openai_chat` ignores provider thinking parameters that the Codex→Chat path already models

**Type:** feature · **Priority:** P2 · **Effort:** M · **Confidence:** high

- **Evidence:** `src-tauri/src/proxy/providers/transform.rs:196-201` — the only reasoning control emitted is `reasoning_effort`, and only when `supports_reasoning_effort(model)` (OpenAI `o*`/`gpt-5*` names, `transform.rs:62-69`). `codex.rs:312-496` contains a full per-vendor reasoning capability model (`thinking:{type}`, `enable_thinking`, `reasoning_split`, OpenRouter `reasoning:{effort}`, DeepSeek/StepFun effort value modes) but it is consumed only by `transform_codex_chat.rs:349-441` via `forwarder.rs:1431-1436`; the Claude branch at `forwarder.rs:1501-1516` → `claude.rs:410-430` never resolves a `CodexChatReasoningConfig`.
- **Problem:** A Claude Code user pointing an `openai_chat` provider at DeepSeek, Qwen/DashScope, GLM, MiniMax, Kimi, SiliconFlow or OpenRouter gets no thinking at all (or uncontrolled default thinking): `thinking:{type:"enabled"}`/`output_config.effort` from Claude Code are dropped on the floor, while the same provider works correctly from Codex. Users see "thinking doesn't work for Claude but works for Codex" with no explanation.
- **Proposal:** Lift `resolve_codex_chat_reasoning_config` + `apply_reasoning_options` into a client-agnostic `chat_reasoning` module that takes a normalized `ReasoningRequest {enabled, effort}` (derived from Anthropic `thinking`/`output_config` via `resolve_reasoning_effort`, or from Responses `reasoning.effort`) and writes the provider-specific fields. Call it from `transform_claude_request_for_api_format` with `provider`.
- **Acceptance:** `transform_claude_request_for_api_format` tests for a DeepSeek provider with `thinking.enabled` emit `thinking:{type:"enabled"}` + `reasoning_effort`, for Qwen emit `enable_thinking:true`, for OpenRouter emit `reasoning:{effort}`; `thinking.disabled` emits the provider's off form.
- **Verification:** **partially-confirmed** — transform.rs:196-201 emits only `reasoning_effort` when `supports_reasoning_effort(model)` (transform.rs:62-69, o-series/gpt-5+) and builds the Chat body from scratch so Anthropic `thinking` is never forwarded; rg confirms `resolve_codex_chat_reasoning_config` (codex.rs:312-496) is consumed only via forwarder.rs:1431-1436 -> transform_codex_chat.rs:349-441 `apply_reasoning_options`, while the Claude branch forwarder.rs:1501-1516 -> claude.rs:410-430 never resolves it, so the gap is real. Details off: the finding omits the existing manual workaround - `meta.localProxyRequestOverrides.body` is merged into the outbound body after transform (forwarder.rs:1528-1536, `apply_local_proxy_body_overrides` at 3210-3250) and is exposed on the Claude form (ProviderForm.tsx:369-374, 548-554, 995-999), so a user can statically inject `thinking:{type:"enabled"}` or `enable_thinking:true`, though it cannot follow Claude Code's per-request thinking toggle or effort. The affected population is also narrower than stated: the built-in Claude presets using `openai_chat` are only OpenCode Go, GitHub Copilot and Nvidia (claudeProviderPresets.ts:375, 1220, 1271), while DeepSeek/Kimi/GLM/MiniMax/Qwen Claude presets use their Anthropic-compatible endpoints, so this mostly hits hand-configured openai_chat providers and OpenRouter/SiliconFlow. The proposal is sound and not implemented (`resolve_reasoning_effort` at transform.rs:85-110 already supplies the Anthropic-side effort input); downgraded to P2 as a feature gap with a workaround rather than a high-severity defect.

### PROV-05: `gpt-5*` models through Chat Completions receive `max_tokens` and raw `temperature`

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** medium

- **Evidence:** `src-tauri/src/proxy/providers/transform.rs:174-185` — `if is_openai_o_series(model) { max_completion_tokens } else { max_tokens }` and unconditional `temperature`/`top_p` passthrough; `transform_codex_chat.rs:288-307` has the identical split. `is_openai_o_series` (`transform.rs:51-55`) only matches `o<digit>`, while `supports_reasoning_effort` (`transform.rs:62-69`) already knows `gpt-5*` is a reasoning family.
- **Problem:** OpenAI's gpt-5 family rejects `max_tokens` ("use max_completion_tokens") and non-default `temperature`/`top_p`; Claude Code sends `temperature: 0` on several background requests, so mapping a Claude model alias to `gpt-5-mini` via `openai_chat` fails with a non-retryable 400. The Responses path is unaffected (`max_output_tokens`), so behaviour differs by `api_format`.
- **Proposal:** Use one `is_openai_reasoning_model()` predicate (o-series + gpt-5*) for both the `max_completion_tokens` switch and for dropping `temperature`/`top_p` (or clamping to 1), applied in both `transform.rs` and `transform_codex_chat.rs`; make the strip opt-out via provider meta for gateways that accept them.
- **Acceptance:** Tests: Anthropic body `{model:"gpt-5.4", max_tokens:100, temperature:0}` → `{max_completion_tokens:100}` and no `temperature`; `gpt-4.1` keeps `max_tokens` and `temperature`; same for the Codex→Chat transform.
- **Verification:** **partially-confirmed** — Code confirmed: transform.rs:176-185 does `if is_openai_o_series(model) { max_completion_tokens } else { max_tokens }` and passes temperature/top_p unconditionally, transform_codex_chat.rs:289-305 is identical, is_openai_o_series (transform.rs:51-55) matches only o<digit> while supports_reasoning_effort (transform.rs:62-69) already treats gpt-5* as reasoning; the production caller is claude.rs:413 (openai_chat branch) and forwarder.rs:2571 buckets 400 as NonRetryable, so no failover. Because Anthropic Messages always carries max_tokens, the max_tokens half alone is a deterministic 400 against OpenAI/Azure directly, independent of the temperature claim. Impact is overstated for P1: no shipped preset pairs gpt-5 with openai_chat (claudeProviderPresets.ts:1220 Copilot, :375 Zhipu, :1271 PIPELLM; the gpt-5.6 Codex preset at :1231-1248 uses openai_responses) and the module's stated target OpenRouter (transform.rs:3) accepts max_tokens, so it needs a user-built openai_chat provider aimed at OpenAI/Azure, which is medium likelihood. The temperature/top_p rejection is model-dependent (gpt-5/5-mini/5-nano and reasoning modes reject non-default values, gpt-5-chat-latest and effort=none models accept them), so the proposed blanket strip by prefix can be lossy and should be the opt-out variant; no ProviderMeta or CodexChatReasoningConfig field for this exists (provider.rs:360-375, 395-515), the only workaround is a static local_proxy_request_overrides.body patch applied after transform (forwarder.rs:1534) that cannot rename max_tokens, and existing tests cover only o1/o3-mini/o4-mini and gpt-4o (transform.rs:1737-1765) while the gpt-5.4 tests (transform.rs:1673-1735) assert reasoning_effort only.

### PROV-06: Gemini bridge never requests or surfaces thinking (no `thinkingConfig`, thought parts discarded)

**Type:** feature · **Priority:** P2 · **Effort:** M · **Confidence:** high

- **Evidence:** `src-tauri/src/proxy/providers/transform_gemini.rs:338-359` — `build_generation_config` maps only `max_tokens/temperature/top_p/stop_sequences`; Anthropic `thinking`, `output_config.effort` and `top_k` are not read anywhere in the file. `transform_gemini.rs:209-211` skips parts with `thought: true`; `streaming_gemini.rs:35-41` filters them out of visible text; neither path emits Anthropic `thinking` blocks, and no `thinkingConfig.includeThoughts` is ever sent.
- **Problem:** Claude Code's extended-thinking controls have no effect on Gemini 2.5/3 models (which think by default, billed as output tokens the user cannot budget), and the model's reasoning is invisible to the user. `top_k` is also silently dropped although Gemini supports `topK`.
- **Proposal:** Map `thinking.enabled/budget_tokens` → `generationConfig.thinkingConfig.{thinkingBudget, includeThoughts:true}`, `thinking.disabled` → `thinkingBudget: 0` (where the model allows), `output_config.effort` → `thinkingLevel` on Gemini 3; emit `thought` parts as Anthropic `thinking` blocks (text-only, no signature) and reuse the shadow/signature envelope for `thoughtSignature` on thought parts. Map `top_k` → `topK`.
- **Acceptance:** Request-transform tests for each thinking shape; stream + non-stream tests where a `thought:true` part becomes a `thinking` block preceding text; usage test confirms `thoughtsTokenCount` still lands in output tokens.

### PROV-07: `GeminiAdapter` sends an empty `Authorization: Bearer ` for refresh-only OAuth JSON

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** `src-tauri/src/proxy/providers/gemini.rs:195-211` — `extract_auth` does `if let Some(creds) = self.parse_oauth_credentials(&key) { Some(AuthInfo::with_access_token(key, creds.access_token)) }`; `parse_oauth_credentials` (`gemini.rs:109-117`) returns `Some` with `access_token: ""` when only `refresh_token` is present. `gemini.rs:237-250` then builds `Bearer {token}` from `auth.access_token` = `Some("")`. `ClaudeAdapter` guards exactly this case (`claude.rs:754-768`, tests at `claude.rs:1197-1250`) but the Gemini-app adapter does not.
- **Problem:** A Gemini-app provider whose `GEMINI_API_KEY` holds an `oauth_creds.json` with an expired/absent `access_token` sends `Authorization: Bearer ` and gets an opaque 401 instead of a clear "token missing, refresh with gemini CLI" diagnostic (or an automatic refresh, see PROV-08).
- **Proposal:** Extract the guard from `claude.rs:741-769` into a shared `gemini_oauth_auth_info(key)` helper used by both adapters; reject empty access tokens with `ProxyError::AuthError` that names the fix.
- **Acceptance:** `gemini.rs` test mirroring `test_extract_auth_gemini_cli_refresh_only_json_does_not_expose_empty_bearer`; both adapters share one implementation.

### PROV-08: Gemini CLI OAuth refresh is not implemented (documented dead code)

**Type:** feature · **Priority:** P2 · **Effort:** M · **Confidence:** high

- **Evidence:** `src-tauri/src/proxy/providers/claude.rs:749-752` — "CC Switch does not currently exchange the refresh_token for a fresh access_token"; `gemini.rs:26-37` — `OAuthCredentials::needs_refresh`/`can_refresh` are `#[allow(dead_code)]` with no caller; no `oauth2`-style token endpoint call exists for Google anywhere in `providers/` (grep for `refresh_token` only hits parsing).
- **Problem:** Gemini CLI tokens expire hourly; every user of the GeminiCli strategy must re-run the gemini CLI and re-paste `oauth_creds.json`, and the proxy can only log a warning (`claude.rs:759-764`). Codex and Copilot both have refresh managers; Gemini is the odd one out.
- **Proposal:** Add a `GeminiOAuthManager` modeled on `CodexOAuthManager` (per-account refresh lock, cached access token, persisted rotated refresh token) using Google's token endpoint with the `client_id`/`client_secret` already parsed from the JSON; have the forwarder resolve the bearer dynamically like it does for `AuthStrategy::CodexOAuth`/`GitHubCopilot`.
- **Acceptance:** Mocked-HTTP tests for refresh success, 401 → re-auth required, and single-flight under concurrency; `needs_refresh/can_refresh` lose `#[allow(dead_code)]`.

### PROV-09: Codex OAuth / Copilot refresh paths lack failure backoff and lose a freshly minted token on persist failure

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** medium

- **Evidence:** `src-tauri/src/proxy/providers/codex_oauth_auth.rs:534-562` — after `refresh_with_token`, a rotated refresh token is written and `self.save_to_disk().await?` runs at line 544 *before* the new access token is cached at 551-560; an IO error returns `Err` and discards the access token while the in-memory refresh token has already rotated. `codex_oauth_auth.rs:476-479` maps 401/403 to `RefreshTokenInvalid` but nothing records the failure, so every subsequent request re-enters the lock and re-calls `auth.openai.com`. Same pattern in `copilot_auth.rs:741-775` (401 → `GitHubTokenInvalid`, no negative cache). `copilot_auth.rs:791-810` caches the `/models` list for the process lifetime with no TTL.
- **Problem:** A transient disk error during rotation costs one user-visible failed request per retry and can brick the account across restarts (disk holds the pre-rotation refresh token); an invalid refresh token causes a thundering-herd of auth calls under Claude Code's parallel subagents; newly enabled Copilot models are invisible until restart.
- **Proposal:** Cache the access token first, then persist (retry persistence in the background); on `RefreshTokenInvalid`/`GitHubTokenInvalid` store a per-account `AuthFailure {at, reason}` and fail fast for N minutes while surfacing "re-authentication required" in `get_status`; add a TTL (e.g. 1h) to the Copilot models cache.
- **Acceptance:** Mocked tests: persist failure still returns the token; two concurrent calls after a 401 make exactly one network call; models cache expires.

### PROV-10: OAuth refresh tokens and GitHub tokens are persisted as plaintext JSON

**Type:** security · **Priority:** P2 · **Effort:** M · **Confidence:** high

### PROV-03: Gemini streaming text uses an ambiguous prefix heuristic that can drop or duplicate text

**Type:** bug · **Priority:** P3 · **Effort:** M · **Confidence:** medium

- **Evidence:** `src-tauri/src/proxy/providers/streaming_gemini.rs:356-399` — `let is_cumulative = visible_text.starts_with(&accumulated_text); let delta = if is_cumulative { visible_text[accumulated_text.len()..] } else { visible_text }`. The module's own tests encode both interpretations: `streaming_gemini.rs:633-645` feeds cumulative chunks (`"Hel"` then `"Hello"`) while `712-725` feeds delta chunks (`"Hel"` then `"lo"`), and both pass only because of the heuristic.
- **Problem:** With the real (incremental) `streamGenerateContent?alt=sse` behaviour, any chunk whose text begins with the entire accumulated text is misread as cumulative: a chunk equal to the previous content (`"\n\n"` after `"\n\n"`, `"}"` after `"}"`, repeated code tokens) yields an empty delta and the text is lost; a chunk like `"}\n"` after `"}"` loses the brace. This is silent corruption of generated code.
- **Proposal:** Decide the mode once per stream rather than per chunk: Gemini API streams are incremental, so append unconditionally; keep cumulative detection only behind an explicit per-provider flag (or detect it by observing that chunk N+1 strictly contains chunk N twice in a row). Also track per-part indices so text emitted after a `functionCall` opens a new text block instead of being merged (see the acknowledged trade-off at `streaming_gemini.rs:495-521`).
- **Acceptance:** Tests: delta chunks `["a", "a"]` → text `"aa"`; `["}", "}\n"]` → `"}}\n"`; cumulative mode only when the provider flag is set; existing shadow-replay tests still pass.
- **Verification:** **partially-confirmed** — streaming_gemini.rs:358-362 computes `is_cumulative = visible_text.starts_with(&accumulated_text)` per chunk and lines 394-398 either replace or append `accumulated_text` (declared at line 245 and never reset), and the tests at 632-645 (cumulative 'Hel'->'Hello') and 711-725 (delta 'Hel'->'lo') do encode both modes, so the ambiguity is real; the comments at 100-101 and 505-507 assert cumulative snapshots while the reviewer asserts incremental, and the squashed history (single commit 6d2ee24) offers no evidence either way. The impact is overstated: the prefix test is against the entire accumulated text, not the previous chunk, so '}' after '}' or repeated code tokens mid-stream cannot trigger it; a misfire requires the whole text so far to be a short string that the very next chunk happens to begin with (realistically only the first one or two visible chunks), after which `accumulated_text` is replaced by that chunk and the stream recovers, and 'duplicate' cannot occur for a genuinely cumulative upstream. Appending unconditionally would break any upstream that really is cumulative (which the authors evidently observed or assumed), so only the per-provider-flag / stream-level-detection variant of the proposal is safe; the per-part-index point is a separately acknowledged trade-off at 495-521. Downgraded to P3: bounded, start-of-response character loss under an unlikely chunking coincidence.

### PROV-30: Shadow/history stores take write locks and clone on every read; prune is O(total calls)

**Type:** performance · **Priority:** P3 · **Effort:** S · **Confidence:** high
