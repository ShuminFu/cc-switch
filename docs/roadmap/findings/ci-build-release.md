# CI/CD, build, release & dependencies — findings (CI-xx)

Part of the [next-phase proposals](../README.md). 48 findings. Priorities: P2 = 40, P3 = 8.

## Area summary

The pipeline already does several hard things well: a five-target release matrix (Windows x64/ARM64, Linux x64/ARM64, macOS universal) with Apple signing + notarization + stapling + verification, Tauri updater artifacts with minisign signatures, a scoped `release` environment, CODEOWNERS-gated `main`, Dependabot across npm/cargo/actions, and a backend CI matrix on three OSes. The main risks are release-integrity and process gaps rather than missing features: Windows installers ship unsigned, the updater endpoint (`/releases/latest/`) can never see a release because every release is created as a prerelease, missing `.sig` files only warn on x64/Linux so a platform can silently drop out of `latest.json`, secrets are interpolated into shell text and the updater private key is exported to `GITHUB_ENV` for every later step, and nothing (no dry-run, no tag-vs-version guard, no `latest.json` validation) stands between a hand-made 4-file bump commit and users' auto-updaters. CI itself is thin: no ESLint (despite CONTRIBUTING documenting `pnpm lint`), no vulnerability/license scanning, no frontend or Tauri bundle build on PRs, no coverage, no `--locked`, and toolchain pins that disagree in three places (rust-toolchain.toml 1.95 vs `rust-version` 1.85 vs CI `@stable`; `.node-version` 22.12 vs CI Node 20 vs "Node 18+" in docs). Dependency hygiene is the biggest hidden build cost: the app's own manifest pins lag what Tauri 2.10 already resolves, producing 79 duplicated crate names and three compiled TLS stacks (OpenSSL via reqwest's default `native-tls`, `ring`, and `aws-lc-rs` via rustls defaults), while mobile-template leftovers (`staticlib`/`cdylib` crate types, Android/iOS icons) and `strip = "symbols"` (which defeats the custom panic-hook backtraces) remain. Suggested direction: (1) harden release integrity first (Windows signing, mandatory signatures, `latest.json` validation, secret scoping, attestations); (2) make the release reproducible and automatable (single version source, bump script, tag guard, `workflow_dispatch` dry-run, generated changelog/release body, package-manager publishing); (3) trim the dependency graph and crate config for build speed; (4) fix the documented-but-missing developer tooling (ESLint, scripts, devcontainer, editorconfig); and (5) as the ambitious moves, a full release-engineering overhaul and a Cargo workspace split of the 147k-LOC crate into core/proxy/cli/tauri-shell so unit tests no longer need GTK/WebKit to run.

## Findings

### CI-01: Windows installers and portable EXE are not code-signed

**Type:** security · **Priority:** P2 · **Effort:** M · **Confidence:** high

- **Evidence:** `.github/workflows/release.yml:260-271` (Windows build), `:439-513` (asset prep) — no `signtool`, Trusted Signing, SignPath or `signCommand` step anywhere; `src-tauri/tauri.conf.json:47-51` only sets `bundle.windows.wix.template`, no `certificateThumbprint`/`signCommand`; `grep -niE 'signtool|attest|trusted.?signing'` over release.yml returns nothing. Contrast with macOS which is fully signed/notarized (`release.yml:189-229`, `352-437`) and advertised as such (`README.md:374`).
- **Problem:** The MSI, ARM64 MSI and portable `cc-switch.exe` ship without an Authenticode signature, so Windows SmartScreen shows "unknown publisher" on every install and every auto-update (the Tauri updater runs the downloaded MSI). Only the minisign signature protects the updater path; the initial download has no integrity/identity guarantee.
- **Proposal:** Add Windows signing via Tauri's `bundle.windows.signCommand` (Azure Trusted Signing with `trusted-signing-cli`, or SignPath's free OSS tier) in a Windows-only step guarded by secret presence so forks still build unsigned; sign both the MSI and the bare EXE before the portable zip is created; verify with `Get-AuthenticodeSignature` in the "Prepare Windows Assets" step and fail if `Status -ne 'Valid'`.
- **Acceptance:** `Get-AuthenticodeSignature CC-Switch-vX-Windows.msi` reports `Valid` for both architectures and the portable EXE; a fresh Windows VM installs the MSI without the SmartScreen "unknown publisher" interstitial.
- **Verification:** **confirmed** — Confirmed: .github/workflows/release.yml:260-271 runs `pnpm tauri build` (x64) / `--bundles msi` (ARM64) with no signing step and :439-513 only copies the MSI and zips the bare `cc-switch.exe`; `grep -niE 'signtool|attest|trusted.?signing|signCommand|certificateThumbprint'` over release.yml, src-tauri/tauri.conf.json and tauri.windows.conf.json returns nothing, and tauri.conf.json:47-51 sets only `bundle.windows.wix.template`. macOS by contrast is signed, notarized and hard-verified at :189-229 and :394-437 and advertised at README.md:374; upstream main's current release.yml still has no Windows signing either. Priority lowered to P2: the MSI is fetched over HTTPS from GitHub and the auto-update path is minisign-protected (tauri.conf.json:63), so this is SmartScreen friction/trust rather than an exploitable gap; it also duplicates PRODUCT-35 in docs/roadmap/README.md:328. Proposal is sound (Tauri 2 supports `bundle.windows.signCommand`; a secret-guarded step keeps forks building).

### CI-02: Updater endpoint points at `/releases/latest/` while every release is published as a prerelease

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** `src-tauri/tauri.conf.json:64-66` endpoint is `https://github.com/farion1231/cc-switch/releases/latest/download/latest.json`; `.github/workflows/release.yml:612` `prerelease: true` unconditionally; `release.yml:734-739` uploads `latest.json` to the tag. GitHub's `latest` alias only resolves to the newest non-prerelease, non-draft release.
- **Problem:** The automated pipeline never produces an update that installed clients can see; a maintainer must manually un-flag "prerelease" in the GitHub UI after smoke-testing. That step is undocumented (no RELEASING.md, see CI-28), unaudited, and the gap between "assets exist" and "updater sees them" is invisible to the workflow, so a forgotten flip silently stalls updates for all users.
- **Proposal:** Make the promotion explicit and automated: either (a) add a `workflow_dispatch` "promote" job that flips `prerelease=false` via `gh release edit --prerelease=false` after a checklist, or (b) decide prerelease-ness from the tag (`v3.17.0-beta.1` → prerelease, `v3.17.0` → full) in `release.yml`. Document whichever is chosen in a RELEASING.md and have the `assemble-latest-json` job print the resolved `releases/latest` URL and `curl -fsS` it (expect 200 after promotion).
- **Acceptance:** Pushing a stable tag yields `curl -fsSL https://github.com/farion1231/cc-switch/releases/latest/download/latest.json | jq .version` == the tag within one workflow run, with no manual UI action.
- **Verification:** **confirmed** — Confirmed: src-tauri/tauri.conf.json:64-66 points the updater at `releases/latest/download/latest.json`, release.yml:612 sets `prerelease: true` unconditionally and :734-739 uploads latest.json to the tag, and GitHub's `latest` alias excludes prereleases, so a fresh run is invisible to installed clients until someone un-flags it. Live check: `curl -I https://github.com/farion1231/cc-switch/releases/latest/download/latest.json` returns 302 to `.../download/v4.0.21/latest.json` while upstream main's release.yml still carries `prerelease: true` (its line 958), proving the manual promotion step exists and is being performed by hand. No RELEASING.md exists and CONTRIBUTING.md (253 lines) has no release/tag mention. Lowered to P2: the failure mode is fail-safe (no update offered, nothing bad ships) and may be an intentional smoke-test gate; proposal (b) tag-derived prerelease plus a resolved-URL check is sound, and src/lib/updater.ts:32-35 ignores `opts.channel`, so no beta channel complicates it.

### CI-03: Missing updater signatures only warn on Windows x64 and Linux, so a platform can silently drop out of `latest.json`

**Type:** bug · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** `.github/workflows/release.yml:466-470` — x64 MSI without `.sig` → `Write-Warning` (ARM64 at `:467` throws); `:528` AppImage `.sig` missing → `echo ".sig for AppImage not found"` and continues; `:314` macOS `.sig` missing → `echo ".sig for macOS not found yet"`; `:672-691` the `latest.json` loop iterates only over `dl/*.sig`, so a platform with no `.sig` is simply omitted (`:700-728` emit keys conditionally). `strategy.fail-fast: false` at `:20`.
- **Problem:** A signing-key hiccup or bundler change that stops emitting `.sig` for one platform does not fail the release; it produces a `latest.json` missing that platform's key, and users on that platform never get the update, with no error anywhere.
- **Proposal:** Make `.sig` mandatory on every platform (throw/`exit 1` like the ARM64 branch), and add a validation step in `assemble-latest-json` that asserts the five expected keys (`darwin-aarch64`, `darwin-x86_64`, `windows-x86_64`, `windows-aarch64`, `linux-x86_64`, `linux-aarch64`) exist, that each URL is an asset of the release (`gh release view --json assets`), and that `jq empty latest.json` succeeds; build the JSON with `jq -n` instead of string concatenation (`:694-731`).
- **Acceptance:** Deleting one `.sig` in a test run fails the workflow before `publish-release`; `jq '.platforms | keys | length' latest.json` == 6 on every successful release.
- **Verification:** **partially-confirmed** — Behaviour confirmed: release.yml:463-470 (x64 `Write-Warning`, ARM64 `throw`), :528 and :314 use `[ -f ... ] && cp ... || echo`, which does not trip `set -euxo pipefail` (:519/:281), :673-691 iterate only `dl/*.sig`, :701-728 emit platform keys conditionally, :20 `fail-fast: false`. The 'signing-key hiccup' scenario is largely mitigated though: :137-141 exits 1 when the key secret is empty, and the Tauri CLI 2.8.1 binary (node_modules/.pnpm/@tauri-apps+cli-linux-x64-gnu@2.8.1) hard-errors with 'A public key has been found, but no private key' / 'failed to sign file' rather than silently skipping `.sig`, so silent omission requires a filename/glob drift between :312/:459/:526 and the `case` patterns at :678-690 or a Tauri bundle-layout change. Upstream main has since made every missing `.sig` an error (its lines 255/315/329/343/648), which supports the proposal; nit: the proposal says 'five expected keys' but lists six (acceptance correctly says 6). P2: low likelihood, moderate impact.

### CI-04: No validation that the Tauri updater can actually consume what the release produced (`latest.json` + minisign verification)

**Type:** test · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** `.github/workflows/release.yml:657-733` hand-assembles `latest.json` via `echo`; `:697` `"notes": "Release $TAG"`; no step runs `minisign -V` or the Tauri CLI against the generated file; `src-tauri/tauri.conf.json:63` holds the public key the clients use. No test in `ci.yml` touches the updater at all.
- **Problem:** The only consumer of `latest.json` is the installed app, so any formatting error, wrong URL (e.g., asset renamed in `:459`, `:526`), or key/signature mismatch is discovered by users, not CI. The static `notes` string also means the in-app update dialog never shows what changed.
- **Proposal:** Add a `verify-updater` job after `assemble-latest-json`: download `latest.json`, for each platform download the asset and run `minisign -Vm <asset> -x <sig-decoded> -P <pubkey from tauri.conf.json>`; assert `.version` equals `tauri.conf.json` version; populate `notes` from `docs/release-notes/v${TAG}-en.md` first paragraph (fallback CHANGELOG). Also add a tiny unit test in `ci.yml` that runs the generation script against fixture `.sig` files.
- **Acceptance:** The verify job fails when a signature or URL is wrong (prove with a deliberately corrupted `.sig` on a test tag) and passes on real releases; `latest.json.notes` is non-static.
- **Verification:** **partially-confirmed** — Confirmed: release.yml:694-731 assemble latest.json by `echo`, :697 hard-codes `"notes": "Release $TAG"`, no `minisign`/`jq` step exists, and ci.yml:1-105 never touches the updater; the live v4.0.21 latest.json indeed has `notes: 'Release v4.0.21'` and the app renders that string (src/lib/updater.ts:43 -> src/components/settings/AboutSection.tsx:945-947), so the static note is user-visible. Missed partial mitigations: the Tauri CLI 2.8.1 binary carries a build-time check 'The updater secret key from `TAURI_SIGNING_PRIVATE_KEY` does not match the public key from `plugins > updater > pubkey`' (worded as a warning, so not a hard gate), and the live latest.json URLs all match the real asset names, so the residual risk is URL/format drift rather than key mismatch. Proposal is sound but `minisign -P` needs the base64-decoded second line of tauri.conf.json:63, and docs/release-notes/v3.17.0-en.md exists as the notes source. P2 as a test/verification gap, not exploitable.

### CI-05: Secrets are interpolated into shell text and the updater private key is exported to `GITHUB_ENV` for all later steps

**Type:** security · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** `.github/workflows/release.yml:137`, `:143`, `:184-185` use `${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}` / `..._PASSWORD` directly in `run:` bodies; `:183` `echo "TAURI_SIGNING_PRIVATE_KEY=$KEY_B64" >> "$GITHUB_ENV"` and `:185` same for the password — these become env for every subsequent step including third-party actions `actions/upload-artifact@v7` (`:563`) and the debug `find` (`:569-574`); `:164` prints the first 10 characters of the raw secret on parse failure (GitHub only masks the full value); `:196`, `:204`, `:207`, `:212`, `:215` inline `APPLE_CERTIFICATE`, `KEYCHAIN_PASSWORD`, `APPLE_CERTIFICATE_PASSWORD`; `:8-9` grants `contents: write` to the whole workflow, including the five build jobs that only need read; `:328` `brew install create-dmg` fetches an unpinned tool during the signed-release path.
- **Problem:** Inline interpolation is the canonical script-injection/quoting hazard (a secret containing `"` or `$` breaks the script), the key in `GITHUB_ENV` widens its exposure to every later action's process environment, the prefix echo leaks key material to logs, and write permissions on build jobs let a compromised dependency/action push to the repo.
- **Proposal:** Pass every secret through step-level `env:` and reference `$VAR`; scope `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)` as `env:` on the three `tauri build` steps only (write the decoded key to `$RUNNER_TEMP` and point `TAURI_SIGNING_PRIVATE_KEY` at the path, which Tauri supports); delete the prefix echo at `:164`; set workflow `permissions: contents: read` and grant `contents: write` only on `publish-release`/`assemble-latest-json` (already declared at `:591-592`, `:640-641`); pin `create-dmg` (`brew install create-dmg@<ver>` is not available, so vendor the script or pin the Homebrew tap commit).
- **Acceptance:** `grep -n 'secrets\.' release.yml` only matches `env:` lines; `GITHUB_ENV` never receives key material; workflow-level permissions are read-only; a run log never contains any secret substring.
- **Verification:** **partially-confirmed** — Facts verified: release.yml:137 and :143 interpolate `${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}` into the script, :183 writes `TAURI_SIGNING_PRIVATE_KEY=$KEY_B64` to `$GITHUB_ENV` and :184-185 the password likewise, :196/:204/:207/:212/:215 inline the Apple secrets, :8-9 grant workflow-level `contents: write` while :591-592 and :640-641 re-declare it, :328 runs an unpinned `brew install create-dmg`, :563 is `actions/upload-artifact@v7`. Impact is overstated: the interpolated values are maintainer-set secrets, not attacker input, so this is quoting hygiene rather than injection; the :164 prefix echo runs only on the unrecognised-format branch and in every realistic key shape prints 'untrusted ' or 'dW50cnVzdG' (the public header), not key material; and the step that must hold the key (:260-275) already runs vite plugins and every crate build script, while later steps are first-party actions or plain `ls`/`find`. The strongest sub-item is workflow `contents: write` combined with `actions/checkout@v6` default persisted credentials (:32-33), which lets a malicious build script push with the token - P2. Proposal is sound: the CLI 2.8.1 help text reads '`TAURI_SIGNING_PRIVATE_KEY`  Path or String of your private key', and upstream main already moved these secrets to `with:` inputs (its lines 191-192).

### CI-06: Version is bumped by hand in four files plus CHANGELOG with no single source and no tag-vs-version guard

**Type:** refactor · **Priority:** P2 · **Effort:** S · **Confidence:** high

- **Evidence:** commit `c154d30 chore(release): v3.17.0` touches `package.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, `CHANGELOG.md`; versions live at `package.json:3`, `src-tauri/Cargo.toml:3`, `src-tauri/tauri.conf.json:4`; `release.yml:3-6` triggers on any `v*` tag and `:663` derives `VERSION="${TAG#v}"` for `latest.json` without comparing it to the config version; no bump script exists in `scripts/` or `package.json:6-17`.
- **Problem:** A tag that does not match the embedded version (e.g., tagging `v3.17.1` on a tree still at 3.17.0) produces binaries reporting one version and a `latest.json` claiming another, which either loops the updater or makes it skip the release. Three hand-edited copies also drift (the Cargo.lock line must be regenerated) and make releases a maintainer-only ritual.

### CI-48: Notarization uses an Apple ID app-specific password on the command line instead of an App Store Connect API key

**Type:** security · **Priority:** P3 · **Effort:** S · **Confidence:** medium

- **Evidence:** `.github/workflows/release.yml:237-239` passes `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` to `tauri build`; `:373-377` `xcrun notarytool submit "$DMG_PATH" --apple-id "$APPLE_ID" --password "$APPLE_PASSWORD" --team-id "$APPLE_TEAM_ID"` puts the password in the process argument list.
- **Problem:** An app-specific password belongs to one person's Apple ID, so if that person loses access the release pipeline breaks, and it cannot be scoped or rotated per pipeline. Passing it as an argv value exposes it to any process on the runner that can list processes. Tauri and notarytool both support API keys (`APPLE_API_KEY`, `APPLE_API_ISSUER`, `APPLE_API_KEY_PATH` / `--key --key-id --issuer`) that are team-owned and revocable.
- **Proposal:** Create a team App Store Connect API key with the Developer role, store the `.p8` as a secret written to `$RUNNER_TEMP`, switch Tauri to `APPLE_API_KEY`/`APPLE_API_ISSUER`/`APPLE_API_KEY_PATH` and notarytool to `--key/--key-id/--issuer`, then delete the Apple ID secrets.
- **Acceptance:** `release.yml` no longer references `APPLE_PASSWORD`/`APPLE_ID`; both app and DMG notarization succeed with the API key; the `.p8` file is removed in the cleanup step.
- **Verification:** added by completeness-critic pass (not independently re-verified)
